# 更新的产品逻辑

本文是更新需求（GitHub issue #131）的产品设计。任何功能都要守住的承诺见 [ADR 0010](../adr/0010-product-promises.md)，为什么这样考虑见 [产品定位](positioning.md)。还没定的只剩文末「暂时不需要决定的」几项。

用户从一个 GitHub 仓库入库技能，背后有三个诉求：跟着作者走、自己掌控、只要一部分。

## 跟着作者走

**用户要什么。** 「我用的是 matt 的那套技能，他现在是什么样，我就要什么样。」用户关心的是整套。

**产品上怎么做**

- **集合要成为看得见的东西，并带上作者身份**：GitHub 头像、`matt/skills`，下面是用户从这里选的几个技能。
- **主操作只有一个：「更新」，作用于整个集合。** 用户想跟上作者时，不该还要逐个技能去点。
- **用户能一眼看出有没有跟上**，而且看的是 Agent 在用的版本，不只是库里的版本。

用户说「更新」，期待的是 Agent 用上新版。所以更新计划里除了库里要变的技能，还列出这些技能装在哪些地方，**一次确认同时完成更新和重新安装**：

```
matt/skills   a1b2c3 → d4e5f6

☑ pdf    有变化   [看差异]
☑ docx   有变化   [看差异]

装在这些地方，一起换成新版：
☑ Claude Code · 全局                     pdf、docx
☑ Codex · ai-workflow-engine            pdf
☐ Claude Code · nextjs-enterprise-app   pdf   ← 你在这里改过，换新版会覆盖你的修改
                                                         [更新]
```

- **装出去的地方默认全选**，用户可以把个别地方勾掉，比如某个项目正在发版，先不动。没勾的地方保持原样。
- **用户改过的地方默认不勾**，并写清原因。用户自己勾上，才算明确同意覆盖。
- **只重新安装这次更新到的技能。**
- **库先换，装出去的地方再逐处换。** 库里的更新要么全部成功，要么什么都不变。之后某一处重新安装失败，不影响库和其他地方；完成后列出没换上的地方和原因，用户可以在那里单独重试。

## 自己掌控

**用户要什么。** 来源怎么改都可以，但不能在用户不知情时进来；进来之后，发现不对还能退回去。

**产品上怎么做**

- **更新计划是一个信任时刻。** 先标出风险：新增或改动的脚本、新增的可执行文件。再给出作者的意图：GitHub 来源附上这段时间的提交说明。最后才是文件差异：SKILL.md 正文按文档展示差异，脚本按代码展示差异。
- **回滚是安全网。** 更新后的提示里带一个回滚入口，之后也能在集合的历史里找到。回滚按次计：一次更新一条记录，各自可以回滚。回滚时库回到那次更新之前的版本，那次更新重新安装过的地方也装回去；之后又被重新安装过、或者被用户改过的地方不动，列出来告诉用户。回滚掉的改动自动算作跳过：不再计入角标，不然在更新页点「全部更新」会把刚退掉的版本又装回去；改主意了照样可以从集合的历史里找回来再更新。
- **「这次先不」和「跳过」是两回事。** 在更新计划里取消勾选，只表示这次先不：这个技能下次还会出现，也仍然计入角标。用户明确不想要这次改动时，用「跳过」。可以跳过单个技能的这次改动，也可以跳过整个来源版本。跳过后不再计入角标，直到来源里这个技能又有了新的改动。跳过的记录留在集合的历史里，改主意了可以从那里找回来再更新。不然角标会一直挂着，过几天就没人再看它。
- **不同来源的审阅深浅**，第一版不按来源区分，统一是「默认展开摘要，点进去才看差异」。

## 只要一部分

**用户要什么。** 仓库里有二十个技能，用户只要其中五个；以后作者再加新技能，也不想被逼着收。

**产品上怎么做**：把两类信息分开，给不同的分量。

| | 分量 | 呈现方式 |
| --- | --- | --- |
| 已入库的技能有新版 | 待办 | 计入角标，出现在更新列表里 |
| 来源里出现了新技能 | 顺带一提 | 不计入角标，只在集合里淡淡提一句「matt 新发布了 2 个技能」 |

- **新技能只算用户上次从这个来源入库之后才出现的。** 用户在 skills.sh 上搜「pdf」，从一个有 30 个技能的仓库里只入库了这一个；另外 29 个是用户见过但没选的，以后不再冒出来。
- **新技能不在更新里入库。** 点「matt 新发布了 2 个技能」，打开这个来源的入库预览，新出现的那几个默认勾上。更新计划回答的是「敢不敢让 Agent 用上新版」；新技能还没装到任何地方，是另一个问题。分开以后，回滚也只需要把技能换回旧版本，不用回答「这次更新带进来的新技能要不要删掉」。
- **提示可以关掉。** 用户点了「不感兴趣」，这几个技能就不再提。

作者删掉或改名的技能，同样是「我的那部分变了」，但语气要平和：

- **删除**：「matt 已从仓库删掉 legacy-helper。你的副本还在，可以继续用。」下面配 [移除] [继续保留]。用户选了保留，之后就不再提醒，只在技能上留一个淡色标记。
- **改名**：「pdf-tools 在来源里好像改名成了 pdf-kit，是同一个吗？」依据是同一来源里一个技能消失、同时出现一个内容大部分相同的技能；GitHub 来源还可以比较两个 commit 之间的文件改名。确认前要说明实际影响：在 Claude Code 里要改用 `/pdf-kit` 调用。
  - 确认：组成员关系、安装记录、版本历史延续到新名字。重新安装时换成新的文件夹名，旧文件夹一并清掉。
  - 否认：按一删一增处理，新名字算作新技能。
  - 推测出来的改名算作已入库技能的变化，计入角标。不然用户只看到「已删除」，会错过作者换了名字的同一个技能。

## 从单个技能发起更新

只做一种更新，从哪里发起只决定默认勾哪些。不管从集合还是从技能发起，打开的都是同一个集合的更新计划：从集合发起时，有变化的技能默认全勾；从技能发起时，默认只勾这一个，其余折叠起来。单个技能更新，就是只勾了一项的集合更新。

用户从技能发起，通常是只想先拿某个紧急修复。在 pdf 的详情页：

```
pdf · 来自 matt/skills · 有新版本                        [更新]
```

点「更新」后：

```
☑ pdf          有变化   [看差异]
─────────────────────────────────
同一来源还有 2 个技能有变化（docx、xlsx）       [展开]
只更新 pdf 后，matt/skills 里的技能会不在同一个来源版本上。
                                         [更新 1 个]
```

- **用户的意图得到尊重。** 从技能进来，默认就只动这一个。
- **集合没有被藏起来。** 同一来源还有别的变化，一眼就能看到，展开就能一起勾上。
- **代价说在前面。** 「会不在同一个来源版本上」在确认前就写清楚，不是事后才发现。

更新后，集合如实显示，不起专门的名字，也不强制对齐：

```
matt/skills   pdf 在 d4e5f6，其余 4 个在 a1b2c3 · 2 个有变化   [更新]
```

下次更新整个集合时自然就对齐了，不需要单独的「对齐」操作。

几个边界情况：

1. **集合里只有一个技能时，照样是一个集合**：左栏和所有技能页照样列出这个来源，和其他集合一样能看来源里的其他技能、看历史、更新；技能上也照样显示「有新版本」。
2. **从技能进入时，改名和删除照样显示**：「可能改名为 pdf-kit」「来源里已删除」，不能只报一句「找不到」。来源里的新技能只在集合里提，从技能进入时不提。
3. **只能更新到来源的最新状态**，不让用户挑某个中间的 commit。要回到旧的，用回滚。
4. **组页面不提供批量更新。** 组里的技能有更新时只显示状态，点进去是该技能所在集合的更新计划。

## 一次典型的更新

1. Dock 角标显示「2」。用户打开 app，侧边栏「更新」旁边有个 2。
2. 进入更新页，每个有新内容的集合占一行：
   ```
   matt/skills       a1b2c3 → d4e5f6 · pdf、docx 有变化 · ⚠ 新增 1 个脚本      [查看] [更新]
   team/agent-kit    3 天前 → 今天     · review 有变化                         [查看] [更新]
                                                                         [全部更新]
   ```
3. 信得过的直接点「更新」，按默认勾选执行：有变化的技能全部更新，装出去的地方里用户没改过的全部换成新版。不放心的点「查看」，打开更新计划：左边是技能列表，右边是风险、提交说明和差异；可以只勾其中几个、勾掉个别地方，也可以跳过这个来源版本。
4. 底部出现提示「已更新 matt/skills，换到了 3 个地方 · 1 个地方你改过，没动 · 回滚」，几秒后消失。没动的地方在技能上照常显示「落后于库里的版本」。

在这个流程里，用户基本不需要在单个技能上操作更新。单个技能那里只显示它和集合的关系，例如「和 matt/skills 同步」「比集合新：只拿了紧急修复」。

## 本地目录和压缩包 URL 来源

**本地目录来源单独处理。** 本地目录作为来源时，作者就是用户自己：在目录里改技能，想尽快在 Agent 里试出效果。更新计划、跳过都用不上，对写技能的人来说会很别扭。所以：

- 不进更新页，不计入角标。
- 技能上只有一个「重新读取」操作：从目录读出当前内容成为新版本，并换到装过它的地方。用户在装出去的文件夹里改过的地方同样不动，完成后告诉用户。
- 底层仍然是一次更新加重新安装，所以照样有版本历史，照样能回滚。

**压缩包 URL 来源和 GitHub 来源走同一套更新计划**，只是没有提交说明，来源版本显示为内容哈希。

## 第一版不做

1. **自动应用更新**：违背「自己掌控」。检查可以自动，应用不行。
2. **单个技能的「检查更新」按钮**：用户关心的是作者，不是单个技能。
3. **按组更新**：一个组跨好几个作者，按组更新会把每个作者的那套都切成一半。组只用来回答「哪些地方要重新安装」。
4. **默认开启系统通知。**
5. **让某个技能长期停在旧版本**（固定）。从技能发起的更新解决的是「这个技能要比集合新」；反过来「这个技能要比集合旧，并且别再提示」会让集合长期处在不同来源版本上，界面还得区分「故意的」和「没跟上的」。先靠跳过和回滚应付，真有人需要再加。

## 怎么判断做对了

任何时候都必须成立的承诺见 [ADR 0010](../adr/0010-product-promises.md)，违反就是 bug。体验则用下面的场景检验，可以拿原型找人试：

| 需求 | 给用户的任务 | 怎样算通过 |
| --- | --- | --- |
| 跟着作者走 | 「matt 昨天发了新版，让你的 Claude Code 用上。」 | 不进任何单个技能就能完成；完成后，用户能在 app 里指出「现在所有地方都是新版」 |
| 自己掌控 | 「这次更新里，有没有你不放心的改动？」 | 不用逐个打开文件，就能找到新增的脚本 |
| 自己掌控 | 「pdf 从上周开始表现奇怪。」 | 能查到是哪次更新改了 pdf，回滚后 Agent 也回到旧版 |
| 只要一部分 | 「matt 新发了两个技能，你没兴趣。」 | 没有因此看到红色角标；过一个月改主意，还能找到这两个技能 |
| 本地目录来源 | 「在目录里改一下这个技能，让 Claude Code 用上。」 | 一个操作就能完成 |

## 暂时不需要决定的

- **通知**：默认只显示角标，系统通知以后再说。
- **按来源设审阅深浅**：第一版不做。
- **集合在界面上叫什么**：做原型时拿几种叫法让人试。

## 术语

已定的术语见 [CONTEXT.md](../../CONTEXT.md)：来源版本、版本、检查更新、更新计划、更新、跳过、回滚。更新时把装出去的地方换成新版，就是重新安装，不另起名字。

不进术语表的说法：

- 「这次先不」只是更新计划里没勾，不是一种状态。
- 「重新读取」是本地目录来源上的按钮文字，背后就是更新加重新安装。
- 集合里的技能不在同一个来源版本上时，直接写「pdf 在 d4e5f6，其余在 a1b2c3」，不起名字。
- 「关注」「跟随」只是日常说法；来源里出现的新技能也不另起名字。

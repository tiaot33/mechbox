# 更新的产品逻辑

本文是对更新需求（GitHub issue #131）的产品分析，**尚未全部定案**。已经定下的承诺见 [ADR 0010](../adr/0010-product-promises.md)，待定的问题和说法列在文末。为什么这样考虑见 [产品定位](positioning.md)。

用户从一个 GitHub 仓库入库技能，背后有三个诉求：跟着作者走、自己掌控、只要一部分。

## 跟着作者走

**用户要什么。** 「我用的是 matt 的那套技能，他现在是什么样，我就要什么样。」用户关心的是整套。

**产品上怎么做**

- **集合要成为看得见的东西，并带上作者身份**：GitHub 头像、`matt/skills`，下面是用户从这里选的几个技能。
- **主操作只有一个：「更新」，作用于整个集合。** 用户想跟上作者时，不该还要逐个技能去点。
- **用户能一眼看出有没有跟上**，而且看的是 Agent 在用的版本，不只是库里的版本。

最后一点是关键分歧。用户说「更新」，期待的是 Agent 用上新版；而 [CONTEXT.md](../../CONTEXT.md) 和 [ADR 0009](../adr/0009-user-flow-fetch-then-install.md) 把更新定义为只改库，装出去的地方要另外重新安装。站在用户的角度，这是同一个流程里的两步，而不是两个功能：

```
更新 matt/skills 完成
这些技能装在 3 个地方，要重新安装成新版吗？
  ☑ Claude Code · 全局
  ☑ Codex · ai-workflow-engine
  ☐ Claude Code · nextjs-enterprise-app   ← 这个项目正在发版，先不动
                               [重新安装]  [以后再说]
```

默认全选，允许把个别地方勾掉。「库里新了，但某个项目先不动」的需求确实存在，但那是例外。

## 自己掌控

**用户要什么。** 来源怎么改都可以，但不能在用户不知情时进来；进来之后，发现不对还能退回去。

**产品上怎么做**

- **更新计划是一个信任时刻。** 先标出风险：新增或改动的脚本、新增的可执行文件。再给出作者的意图：GitHub 来源附上这段时间的提交说明。最后才是文件差异：SKILL.md 正文按文档展示差异，脚本按代码展示差异。
- **回滚是安全网。** 更新后的提示里带一个回滚入口，之后也能在集合的历史里找到。
- **这次不跟。** 来源的某个来源版本有破坏性改动时，用户可以跳过它。之后来源再有新的来源版本，才重新提示。不然角标会一直挂着，过几天就没人再看它。
- **不同来源的审阅深浅**，第一版不按来源区分，统一是「默认展开摘要，点进去才看差异」。

## 只要一部分

**用户要什么。** 仓库里有二十个技能，用户只要其中五个；以后作者再加新技能，也不想被逼着收。

**产品上怎么做**：把两类信息分开，给不同的分量。

| | 分量 | 呈现方式 |
| --- | --- | --- |
| 已入库的技能有新版 | 待办 | 计入角标，出现在更新列表里 |
| 来源里出现了新技能 | 顺带一提 | 不计入角标，只在集合里淡淡提一句「matt 新发布了 2 个技能」，点开可以入库 |

用户见过但没选的技能，以后不再冒出来。

作者删掉或改名的技能，同样是「我的那部分变了」，但语气要平和：

- **删除**：「matt 已从仓库删掉 legacy-helper。你的副本还在，可以继续用。」下面配 [移除] [继续保留]。用户选了保留，之后就不再提醒，只在技能上留一个淡色标记。
- **改名**：「pdf-tools 在来源里好像改名成了 pdf-kit，是同一个吗？」确认前要说明实际影响：在 Claude Code 里要改用 `/pdf-kit` 调用。

## 一次典型的更新

1. Dock 角标显示「2」。用户打开 app，侧边栏「更新」旁边有个 2。
2. 进入更新页，每个有新内容的集合占一行：
   ```
   matt/skills       a1b2c3 → d4e5f6 · pdf、docx 有变化 · ⚠ 新增 1 个脚本      [查看] [更新]
   team/agent-kit    3 天前 → 今天     · review 有变化                         [查看] [更新]
                                                                         [全部更新]
   ```
3. 信得过的直接点「更新」。不放心的点「查看」，打开更新计划：左边是技能列表，右边是风险、提交说明和差异；可以只勾其中几个，也可以跳过这个来源版本。
4. 更新完，接上「要重新安装成新版吗」。
5. 底部出现提示「已更新 matt/skills · 回滚」，几秒后消失。

在这个流程里，用户基本不需要在单个技能上操作更新。单个技能那里只显示它和集合的关系，例如「和 matt/skills 同步」「比集合新：只拿了紧急修复」。

## 本地目录来源

本地目录作为来源时，作者就是用户自己：在目录里改技能，想尽快在 Agent 里试出效果。更新计划、跳过、回滚都用不上，用户要的是一个「重新读取并装上」的快捷操作。把它和 GitHub 来源塞进同一套审阅流程，对写技能的人来说会很别扭。

## 第一版不做

1. **自动应用更新**：违背「自己掌控」。检查可以自动，应用不行。
2. **单个技能的「检查更新」按钮**：用户关心的是作者，不是单个技能。
3. **按组更新**：一个组跨好几个作者，按组更新会把每个作者的那套都切成一半。组只用来回答「哪些地方要重新安装」。
4. **默认开启系统通知。**

## 怎么判断做对了

任何时候都必须成立的承诺见 [ADR 0010](../adr/0010-product-promises.md)，违反就是 bug。体验则用下面的场景检验，可以拿原型找人试：

| 需求 | 给用户的任务 | 怎样算通过 |
| --- | --- | --- |
| 跟着作者走 | 「matt 昨天发了新版，让你的 Claude Code 用上。」 | 不进任何单个技能就能完成；完成后，用户能在 app 里指出「现在所有地方都是新版」 |
| 自己掌控 | 「这次更新里，有没有你不放心的改动？」 | 不用逐个打开文件，就能找到新增的脚本 |
| 自己掌控 | 「pdf 从上周开始表现奇怪。」 | 能查到是哪次更新改了 pdf，回滚后 Agent 也回到旧版 |
| 只要一部分 | 「matt 新发了两个技能，你没兴趣。」 | 没有因此看到红色角标；过一个月改主意，还能找到这两个技能 |
| 本地目录来源 | 「在目录里改一下这个技能，让 Claude Code 用上。」 | 一个操作就能完成 |

## 待定的产品问题

按影响大小排列，后面的问题依赖前面的答案。

1. **更新是否默认接上重新安装。**
   - 选项一：两步合成一个流程，默认全选、可以勾掉。最符合「跟着作者走」，但 CONTEXT.md 和 ADR 0009 里「更新只改库」的说法要改成「库和装出去的地方分两次确认」。
   - 选项二：保持两个独立的功能。概念最干净，但用户以为已经更新了，Agent 其实还在用旧版。
   - 建议：选项一。
2. **回滚是否连带重新安装。** 如果第 1 条选了选项一，回滚却只改库，Agent 的行为就不会恢复。建议：那次更新后重新安装过的地方，回滚时也重新安装回去；之后又被换过或被用户改过的地方不动，并列出来告诉用户。
3. **更新后的重新安装碰到用户改过的文件夹怎么办。** 可以默认不勾并注明「你在这里改过，换新版会覆盖你的修改」，也可以跳过后再告知，或者照常覆盖（违反 ADR 0010）。建议：默认不勾，并写清原因。
4. **新技能是否从「更新」里拆出来，以及从市场只入库一个技能时怎么办。** 用户在 skills.sh 上搜「pdf」，从一个有 30 个技能的仓库里只入库了这一个，入库预览时也只看到了这一个。之后把另外 29 个都当新技能列出来，就是噪音。建议：新技能不计入角标，而且只算入库之后才出现在来源里的。
5. **要不要能跳过一个来源版本。** 不做的话，角标会一直挂着，失去意义；做的话会多一种状态，被跳过的来源版本要能在集合的历史里找回来。建议：做。
6. **本地目录来源是否单独处理。** 单独处理的话，只给一个「重新读取并装上」的操作，不进更新页、不计入角标；不单独处理则概念统一，但写技能的人每次都要走一遍审阅。建议：单独处理。

暂时不需要决定的：

- **通知**：默认只显示角标，系统通知以后再说。
- **按来源设审阅深浅**：第一版不做。
- **集合在界面上叫什么**：做原型时拿几种叫法让人试。

## 术语

已定的术语见 [CONTEXT.md](../../CONTEXT.md)：来源版本、版本、检查更新、更新计划、回滚。更新后把装出去的地方换成新版，就是重新安装，不另起名字。

还没定的说法：

- 「跳过」一个来源版本、「开发中的技能」：等上面对应的产品问题定了再定。
- 集合在界面上的叫法：等原型验证。

「关注」「跟随」只是日常说法，不进术语表；来源里出现的新技能也不另起名字。

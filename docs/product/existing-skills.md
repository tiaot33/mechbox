# Agent 目录里已有技能的产品逻辑

本文是 GitHub issue #183 的产品设计：认出 Agent 目录里的未纳管技能：不是库装的能入库，库装出去又被改过的能用这份修改更新库里的技能。任何功能都要守住的承诺见 [ADR 0010](../adr/0010-product-promises.md)，为什么这样考虑见 [产品定位](positioning.md)，更新、跳过、回滚的逻辑见 [更新的产品逻辑](update.md)。留到实现时定的列在文末。

产品定位里有三种时刻和这件事直接相关：

- **第一次打开**：用户早就用命令行工具或手动拷贝装了一批技能。
- **Agent 表现怪了**：想知道 Agent 在这个项目里到底看到了哪些技能。
- **新项目、新机器**：想把常用的技能都带过去，包括手动拷的。

另外还有一个日常习惯：用户（或 Agent 自己）会直接在 Agent 目录里改技能。

背后是三个诉求：把已有的接过去、看清 Agent 实际看到什么、在哪改都算数。

## 把已有的接过去

**用户要什么。** 「我已经在用这些技能了，别让我重来一遍。接过去以后，Agent 的表现一点都不能变。」

**产品上怎么做**

- **入库不改变 Agent 用的东西。** 磁盘上一个字节都不动。入库以后，Agent 在每个项目里用的技能和之前完全一样，app 只是开始知道它们。这是用户敢一次全选的前提。
- **一次确认就全部入库，默认全选（在项目仓库里的、指向 Agent 目录以外的除外）。** 在这台机器上第一次打开 app 时，直接把用户带到各 Agent 全局目录里的未纳管技能；之后每登记一个项目，直接带到这个项目里的。换到新机器也一样。第一次打开时只看得到全局目录，很多人的技能主要在项目里，所以要写一句：项目里的技能，登记项目时再接。之后也能在作用域里逐个入库。
- **不记「问过没有」。** 不记哪些作用域问过、当时看到了哪些技能。用户要的只有两条：第一次被带着接过去，之后不被催。第一次由打开 app、登记项目这两个时刻带出来；之后作用域里一直淡淡显示还有几个不是库装的技能没入库，从这里同样可以全部入库或逐个入库。
- **按作者分组。** 用户心里的单位是作者的那一套。确认列表按认出的来源分组，例如「matt/skills · 5 个」，认不出来源的单独一组。用户扫一眼就敢全选，也提前看到了入库后的集合。
- **话按分量说。** 用户敢全选，靠的是第一句「磁盘上什么都不改，Agent 用的和现在一样」；接着是唯一的代价（见下文「说清楚以后由谁来管」）。在项目仓库里的提醒只在用户勾上那一项时出现，同名冲突只在有冲突时出现。最常见的情况是全局目录、没有冲突，看一眼、点一下就完成。
- **同名但内容不同，不合成一个技能。** 同一个技能名在几个作用域里内容不一样时，确认时把冲突单列出来，默认入库最近修改的那份；其余的仍是未纳管技能，照样看得见、不被覆盖，用户想要哪份，之后再入库。不把几份入库成同一个技能的不同版本：较旧的那份会显示成「落后于库里的版本」，下次更新时默认被勾上、覆盖掉，而用户可能是故意给某个项目留了一份变体。内容完全一致的，入库成一个技能，各处都记为安装。
- **一个失败不拖累其余。** 能入库的照常入库；读不成来源的单列出来，让用户重试、改链接或清空来源（见下文「认出的来源在确认前给用户看」）。读来源要等时，用户能看到在等什么。
- **能认出作者的，接过来以后照常跟着作者走。** 用户用 `npx skills add` 装的技能，本来就是在跟某个作者，入库后要进对应的集合，照常检查更新。用户要的是 app 接手，不是把技能和作者的联系切断。认不出作者的，用户可以给一个来源链接；不给的，按下文「作者就是用户自己」处理。
  - **和作者现在的一样**：就是作者的那一版。
  - **不一样，但能确认是当初装的原样**（`npx skills` 记下的哈希对得上）：是作者的旧版，照常显示有更新。`npx skills` 不会自动更新，这是最常见的情况；要是当成用户改过，这批技能会一直显示已是最新，跟着作者走就落空了。
  - **不一样，但能确认装的就是作者现在这一版**（`npx skills` 记下的哈希对不上磁盘，却等于作者现在的那一版）：磁盘不一样是用户后来改的，作者之后没动过。当作用户在作者现在这一版上的修改，和「用目录里的修改更新」之后一样：第一次检查更新显示没有更新；等作者再改，才写清「更新会换掉你的修改」，默认不勾。要是报有新版本，用户点开只会看到作者那边什么都没变。
  - **不一样，又说不清是不是改过**（没有哈希，或哈希哪一版都对不上）：入库后先报一次有新版本，写清「更新会换掉你的修改」，默认不勾；跳过就消失，直到作者再改。当初装的是哪一版不知道，就不能断言作者之后没改过。
  - **认出的来源在确认前给用户看**：写清以后跟着谁检查更新，用户可以改链接，也可以清空。读不成来源时说出来，让用户重试、改链接或清空，不悄悄当成没有来源的技能：之后没办法再给它补上来源，等于悄悄切断了和作者的联系。
  - **库里已有这个作者的同名技能、内容又对不上时，不合并**，理由同上文「同名但内容不同」；用户可以清空来源，作为没有来源的技能入库。
- **说清楚以后由谁来管。** 入库就是把技能交给 app，这一点要在确认时说出来。用户之后要是还用命令行工具更新这些技能，app 只能把它们当作「被手动改过」。这是用户在点确认前需要知道的代价。
- **不是用户的，默认不接。** 提交在项目仓库里的技能归团队管，照样列出，标明「在项目仓库里」，默认不入库。项目里 `skills-lock.json` 记录的技能也一样：这份来源记录提交在仓库里，技能是团队约定装的。用户自己勾上才入库，确认时写清：之后在 app 里更新它，会改动项目仓库里的文件。
- **接过来以后，符号链接换成独立的一份，但先说出来。** `npx skills` 把真实文件夹放在 `~/.agents/skills`，再从其他 Agent 的目录链过去，为的是由它统一更新。交给 app 以后，各处由 app 一起更新，链接就不需要了。入库时照样不动；app 第一次要写这一处时（更新、重新安装、回滚），在确认里写明这里原来是指向哪里的符号链接、之后会变成独立的一份。app 要删一个被链接指向的真实文件夹时（比如从 Codex 卸载，Claude Code 里还链着它），先给链着它的那一处换上独立的一份，不让另一个 Agent 的技能跟着没了。为什么不一直保留链接，见 [ADR 0012](../adr/0012-symlinks-become-own-folders-after-takeover.md)。
- **指向 Agent 目录以外的符号链接，默认不接。** 技能作者常把 Agent 目录里的技能链到自己的工作目录，在那里改了，Agent 马上就能用上。接过来以后链接一换，这个习惯就断了。所以照样列出、写明指向哪里，默认不入库；用户自己勾上时写清：之后在 app 里更新，会把这个链接换成独立的一份，在工作目录里改就不再影响这里。
- **没入库的，不再催。** 用户没勾的技能不是待办，不计入角标，只算在作用域里那一行淡淡的数字里；在项目仓库里的、指向 Agent 目录以外的不算进去，不然团队仓库和作者自己的作用域会一直挂着一个数。

## 看清 Agent 实际看到什么

**用户要什么。** 「pdf 在这个项目里表现得不对，是不是用的不是我以为的那个？」

**产品上怎么做**

- **按作用域列全。** 库管着的和未纳管的放在一起，能一眼区分。只列 app 装的，等于给了用户错误的安心。
- **同名要说出后果。** 不能只标一个「同名」，要说清在这个 Agent 里会怎样：Claude Code 里全局那个生效，Codex 里两份都会出现。用户排查时要的是答案，不是线索。
- **只看，不替用户删。** 不是库装的未纳管技能，只提供在 Finder 中显示。

## 在哪改都算数

**用户要什么。** 「我在 Claude Code 的目录里改了一句，想让 Codex 也用上，换机器也带着。作者以后再发新版，别悄悄把我的修改盖掉。」

**产品上怎么做**

- **留下目录里的修改，就是一次更新。** 库装出去的技能被改过，也是未纳管技能。用户想留下修改，期待的是别的地方也用上，就像说「更新」时期待 Agent 用上新版。所以：
  - 确认时列出这个技能还装在哪些地方，默认一起换成这份修改，用户改过的地方默认不勾；
  - 留一条记录，能回滚。
- **改了作者的技能，照样跟着作者走。** 作者发了新版，照常出现在更新列表里，但写清楚「更新会换掉你的修改」，默认不勾。不想要就用跳过，角标消失，直到作者再改。不另外造一个「不再跟随」的状态：让技能长期停在某个版本，更新的产品逻辑里已经决定第一版不做。
- **有没有新版，只看作者那边。** 判断的是「作者从你改的那一版之后有没有改过」，而不是「库里的和作者的不一样」。不然用户一用修改更新，就永远挂着「有更新」。
- **没有来源的技能，作者就是用户自己。** 这和本地目录来源是同一种用户：在目录里改，想尽快在 Agent 里试出效果。照搬那里的体验：不进更新页，不计入角标，只有一个用目录里的修改更新的操作，作用和本地目录来源的「重新读取」一样。用户不需要再学一种新的技能类型。

## 怎么判断做对了

| 给用户的任务 | 怎样算通过 |
| --- | --- |
| 「第一次打开 app，把你在用的技能都交给它管。」 | 一次确认完成；之后 Agent 在每个项目里的表现都没变，也能把这些技能装到另一个项目 |
| 「Claude Code 在这个项目里有哪些技能？」 | 列得全，包括未纳管技能 |
| 「pdf 在这个项目里表现得不像你装的版本。」 | 能发现全局有一个同名的，并知道哪个生效 |
| 「换台机器，把你的技能都带过去。」 | 原来手动拷的技能也带过去了 |
| 「你在 Claude Code 的目录里改了一个技能，让 Codex 也用上。」 | 一次确认完成 |
| 「你改过 pdf 里的一句话，作者又发了新版。」 | 能看出更新会换掉你的修改；不想要就跳过，角标消失 |

## 留到实现时定的

- **按钮和提示的文字**：第一次打开和登记项目后带用户入库的那一屏、作用域里那一行淡淡的提示、未纳管技能上的入库按钮、用目录里的修改更新的按钮，由实现时提出，审查时定。

## 不在范围内

- 插件里的技能、企业托管目录和 Codex 的 ADMIN / SYSTEM 技能：由各自的系统管理，用户在 app 里管不了。
- 没有登记的项目。
- 新机器上把库里的技能装到这台机器。新机器上第一次打开时用户更想要的是这件事，它另行设计时，要和这里带用户入库的那一屏放在一处，不先后各弹一次。
- 推算完整的生效规则（插件是否启用、frontmatter 里关闭自动调用等），只标出同名。
- 自动监视 Agent 目录变化并自动入库或更新。

## 术语

已定的术语见 [CONTEXT.md](../../CONTEXT.md)：未纳管技能、入库、作用域、已登记项目、集合、检查更新、更新计划、更新、跳过、回滚、重新安装。

不进术语表的说法：

- 「把已有的接过去」「作者那边有没有改过」只是本文的描述，不是界面上的概念。
- 「用目录里的修改更新」是更新的一种，不另起名字。

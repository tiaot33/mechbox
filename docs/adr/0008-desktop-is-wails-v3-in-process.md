# 桌面端用 Wails v3，与库在同一个进程里

v1 只有桌面端这一个界面。它是一个 Wails v3 应用：Go 进程直接持有库，React 前端经 Wails 绑定调用 `*library.Library` 的方法，不另起子进程，也不建 RPC 层。工具是单用户、在本机使用的，跨进程通信的成本换不来任何好处。

## 决定

- **库只通过 `*library.Library` 对外。** 实现子包（存储、来源、Agent 目录、S3 等）放在 `internal/library/internal/` 下，Go 的 internal 规则让桌面端无法导入它们，由编译器保证前端只调用库。Wails 绑定时，参数和返回值都经过 JSON 传递，前端的 TypeScript 类型也由绑定自动生成，所以库方法的参数和返回值类型都必须能经 JSON 往返。
  - 作用域因此是一个带显式类型字段的结构体，而不是 Go 接口。
  - 错误也按同样的思路处理：`ErrorOf` 把任意错误规范成带码的错误，桌面端只调用它，归类规则只在库里写一份。
- **慢操作可以中途取消。** 入库预览、入库、更新、同步都可能很慢。用户在前端取消时，Wails 会取消对应调用的 `ctx`，库据此停下来。所以库的每个方法都以 `ctx` 开头，同步返回结果和错误。进度计划由库通过 `ctx` 携带的回调报告，再由桌面端转成事件，目前尚未实现。
- **选 v3，不选稳定的 v2。** v3 支持按次取消调用，能把错误以结构化 JSON 传到前端，还能把具名字符串类型生成为 TypeScript 枚举。这些 v2 都做不到，v2 也无法为接口类型的参数生成绑定。
  - 选定时 v3 仍是 beta，所以钉住具体版本。
  - 如果 beta 的变动阻塞了开发，且短期内跟不上，就退回 v2。退回后，错误编码成 JSON 字符串传递，取消由桌面端自己管理。
- **单实例运行。** 只有这一个进程写库，所以不做跨进程的变更通知；前端在自己完成写操作后重新读取数据。
- **平台**：macOS 优先支持；Windows 和 Linux 只保证能编译。
- **前端技术栈**：React + TypeScript + Vite，组件用 shadcn/ui(底层 Radix),样式用 Tailwind CSS。
  - 起初样式照 UI 原型手写在一份 CSS 里。界面变多以后，同一种按钮的规则散在文件各处、靠后面追加的覆盖前面的，新界面又各自起一次性的类名，外观逐渐不一致；弹窗、抽屉、下拉也都要自己处理焦点和 Esc。所以改成组件化：同一种控件只有一份实现，样式和组件写在一起。
  - 外观仍以 UI 原型为准。毛玻璃来自窗口背后的 macOS 原生层，界面只用半透明白色让它透出来；原型的颜色、圆角、阴影定成 Tailwind 主题，shadcn 组件的默认样式(不透明背景、深色遮罩)一律换成主题里的值，不照搬。
- **代码位置**：`cmd/desktop/`，Go 入口、`frontend/` 和构建配置都放在这里。
  - 前端放在 Go 入口的目录下，是因为 `go:embed` 不能引用包目录以外的文件。
  - Wails 专属的代码（绑定、事件、窗口）都留在这里，库不依赖 Wails。原则是应用依赖库，库不依赖应用。

## 考虑过的选项

- **Electron + Go 子进程**（经 stdio 通信，走 JSON-RPC）：各平台渲染一致，生态最大。但接界面之前，要先建好完整的 RPC 层和 TypeScript 类型生成；发布时还要附带 Chromium 和 Node。我们以 macOS 为主，渲染一致性带来的好处不大。
- **Tauri + Go 子进程**：包体小，但同样要建 RPC 层，还多了一条 Rust 工具链。
- **常驻后台进程持有库，多个界面经本机 socket 连接**：多个界面同时存在时，这是正确的形态。但它要管理后台进程的生命周期，而眼下只有一个界面，用不上。
- **Wails v2**：原因见上文"选 v3，不选稳定的 v2"。

## 后果

- 从 Finder 或 Dock 启动的 macOS 应用读不到 shell 环境变量，`PATH` 里也没有 Homebrew。所以配置与凭证都在设置页填写、存在数据库里，不读环境变量（[ADR 0011](0011-settings-live-in-the-database.md)）。
- 以后如果出现别的进程也要使用库，比如终端界面、命令行、多开，到时再决定跨进程的变更通知和通信方式。

# 桌面端用 Wails v3，与库在同一个进程里

v1 只有桌面端这一个界面。它是一个 Wails v3 应用：Go 进程直接持有库，React 前端经 Wails 绑定调用 `api.go` 里的接口，不另起子进程，也不建 RPC 层。工具是单用户、在本机使用的，跨进程通信的成本换不来任何好处。

## 决定

- **库只通过 `api.go` 里的一个 Go 接口对外。** Wails 绑定时，参数和返回值都经过 JSON 传递，前端的 TypeScript 类型也由绑定自动生成，所以接口里的类型都必须能经 JSON 往返。
  - 作用域因此是一个带显式类型字段的结构体，而不是 Go 接口。
  - 错误也按同样的思路处理：`ErrorOf` 把任意错误规范成带码的错误，桌面端只调用它，归类规则只在库里写一份。
- **慢操作可以中途取消。** 预览、入库、更新、同步都可能很慢。用户在前端取消时，Wails 会取消对应调用的 `ctx`，库据此停下来。所以接口的每个方法都以 `ctx` 开头，同步返回结果和错误。进度计划由库通过 `ctx` 携带的回调报告，再由桌面端转成事件，目前尚未实现。
- **选 v3，不选稳定的 v2。** v3 支持按次取消调用，能把错误以结构化 JSON 传到前端，还能把具名字符串类型生成为 TypeScript 枚举。这些 v2 都做不到，v2 也无法为接口类型的参数生成绑定。
  - 选定时 v3 仍是 beta，所以钉住具体版本。
  - 如果 beta 的变动阻塞了开发，且短期内跟不上，就退回 v2。退回后，错误编码成 JSON 字符串传递，取消由桌面端自己管理。
- **单实例运行。** 只有这一个进程写库，所以不做跨进程的变更通知；前端在自己完成写操作后重新读取数据。
- **平台**：macOS 优先支持；Windows 和 Linux 只保证能编译。
- **前端技术栈**：React + TypeScript + Vite + shadcn/ui + Tailwind CSS。
- **代码位置**：`cmd/desktop/`，Go 入口、`frontend/` 和构建配置都放在这里。
  - 前端放在 Go 入口的目录下，是因为 `go:embed` 不能引用包目录以外的文件。
  - Wails 专属的代码（绑定、事件、窗口）都留在这里，库不依赖 Wails。原则是应用依赖库，库不依赖应用。

## 考虑过的选项

- **Electron + Go 子进程**（经 stdio 通信，走 JSON-RPC）：各平台渲染一致，生态最大。但接界面之前，要先建好完整的 RPC 层和 TypeScript 类型生成；发布时还要附带 Chromium 和 Node。我们以 macOS 为主，渲染一致性带来的好处不大。
- **Tauri + Go 子进程**：包体小，但同样要建 RPC 层，还多了一条 Rust 工具链。
- **常驻后台进程持有库，多个界面经本机 socket 连接**：多个界面同时存在时，这是正确的形态。但它要管理后台进程的生命周期，而眼下只有一个界面，用不上。
- **Wails v2**：原因见上文"选 v3，不选稳定的 v2"。

## 后果

- 从 Finder 或 Dock 启动的 macOS 应用读不到 shell 环境变量，`PATH` 里也没有 Homebrew。库目前靠环境变量和 `gh` 获取配置与凭证，所以打包后的桌面端需要另外的运行时配置才能用。
- 以后如果出现别的进程也要使用库，比如终端界面、命令行、多开，到时再决定跨进程的变更通知和通信方式。

# 已有技能按内容识别：与库一致的自动纳入，同名异内容不合并

Agent 目录（各 Agent 的全局目录和各已登记项目里的目录）里不是由库安装的技能文件夹，按内容决定它是不是库里的技能，以及是否自动纳入管理：

- **按内容认出同一个技能和版本。** 文件路径和内容都相同就算一样，不比可执行位，各平台一样；也不看这个作用域装没装过这个技能。巡检、检查更新判断内容变没变也按同样的规则：只改了可执行位不算用户改过，也不算作者出了新版。符号链接按它指向的内容比对。库里几个技能的某一版内容一模一样时，同样的内容总是认作同一个技能。
- **与库里任意一版内容一致的，自动纳入管理，不用再入库。** app 看到它时自动记为该技能装在这个作用域（与当前版本一致巡检为当前版本，与旧版一致巡检为落后），磁盘上不改任何字节，符号链接保持原样。后续巡检、更新、重新安装、回滚、卸载、移除技能照常包括这一处。一个技能在一个作用域里仍只记一处安装。
- **三类例外既不自动纳入，也不在入库确认里默认勾选**（与库里内容一致时仍显示在库里该技能下，但须用户手动勾选或点入库才记为安装）：
  - **已提交进项目 git 仓库的技能**：归项目团队版本控制管理，纳入后在 app 里更新会直接改动仓库里的文件；
  - **登记在项目 `skills-lock.json` 里的技能**：`npx skills` 在项目里写下的团队约定锁文件，即便技能文件夹本身未提交进 git，同样归项目仓库管理；
  - **指向 Agent 目录以外的符号链接**：例如技能作者把 `~/.claude/skills/foo` 链到自己的本地工作目录 `~/code/my-skills/foo` 以便修改实时生效，接管后首次写入会把链接换成独立文件夹（见 [ADR 0012](0012-symlinks-become-own-folders-after-takeover.md)），会切断这个工作流。
- **与库里任何一版都对不上的，不强行合并。**
  - 内容与该技能来源里作者最新版一致、且比库里新的：认作在 app 外更新到的新版，走集合的更新计划，不自动纳入；
  - 其余同名但内容不同的（无论跨作用域同名，还是与库里已有同作者技能同名但内容对不上）：绝不合并成同一个技能的不同版本，避免把用户为某个项目故意保留的变体标成落后、在下次更新时覆盖掉。
- **认来源时只取优先级最高的一级。** 先用库里内容完全一致的技能的来源（它没有来源就不带来源），其次用 `npx skills` 来源记录，最后去 skills.sh 比对（库里已在跟的来源优先，按集合先后、内容相似度与 skills.sh 排序）。同样内容不管在几处、何时识别，认出的都是同一个来源。

产品层面的引导流程、同名排查与本地修改回流见 [Agent 目录里已有技能的产品逻辑](../product/existing-skills.md)。

## 考虑过的选项

- **内容一致也不自动接管，都要用户确认才补记安装（原设计）。** 这一步是多余的：技能已经在库里，用户第一次打开 app 或登记项目时还要多看一组「已在库里」的确认项；不点的话，库里明明有这个技能，Agent 用的那份却一直不被管、之后跟着停在旧版。自动纳入不改动磁盘上任何字节，满足 [ADR 0010](0010-product-promises.md)「用户没有点头，Agent 用的技能就不变」；纳入后用户在目录里改了内容，仍会报为用户改过、不悄悄覆盖。
- **按技能名把同名但内容不同的文件夹合并成同一技能的不同版本。** 较旧或不同的那一份会被显示为「落后于库里的版本」，在下次更新时默认勾选覆盖掉，破坏用户故意留给某个项目的变体。
- **把项目仓库里、`skills-lock.json` 里或指向 Agent 目录以外的软链接也一并自动纳入。** 会在用户不知情时接管团队共管文件，或在后续写入时悄悄切断作者本地开发联调。

## 后果

- 整批入库的确认里不再出现已自动纳入的技能；「已在库里、只补记安装」只剩上述三类例外。
- 自动纳入后，用户在文件夹里改了内容，巡检报为用户改过，更新默认不覆盖；移除技能时这一处和其他安装一样列在确认里。
- 文件夹内容与作者来源里最新版一致、但库里还没有这一版时，不自动纳入，照旧引导通过更新把库里的技能换成这一版。
- 同一个作用域里已经记了一处安装时，别的内容一致的文件夹仍认作这个技能，显示在它下面，但不重复记录：入库时不另记，整批入库的确认里也没有它。
- 符号链接自动纳入或入库后何时转为独立文件夹，见 [ADR 0012](0012-symlinks-become-own-folders-after-takeover.md)。

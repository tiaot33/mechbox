# 凭证只存在这台机器上：令牌和密钥进系统的钥匙串、凭据管理器或密钥环，其余进应用设置

从访达或 Dock 启动的桌面端读不到 shell 里的环境变量（[ADR 0008](0008-desktop-is-wails-v3-in-process.md) 的后果），所以设置页可以填 GitHub 个人访问令牌和同步用的 S3 设置。这些凭证只存在这台机器上：

- **GitHub 令牌、Secret Access Key、Session Token** 存在系统里:macOS 存在钥匙串里,Windows 存在凭据管理器里，Linux 存在系统密钥环里(D-Bus 上的 Secret Service,如 GNOME Keyring、KWallet)。
- **服务地址、存储桶、对象名、区域、Access Key ID** 和检查更新、通用这些设置一样，存在数据库旁边的应用设置文件 `settings.json` 里。

应用启动时和用户保存后，桌面端把它们交给库。库只在这次运行里持有，不写进数据库。

设置页填的只是多一个来源，环境变量照旧有效：

- 令牌没填时，库读 `GITHUB_TOKEN` / `GH_TOKEN`。
- 同步设置整组取用：填了任意一项就整组用设置页的；全部留空时才读 `SKILLS_S3_*`、`AWS_*`，不逐项拼接。

## 为什么不进数据库

数据库会整库推送到 S3，凭证放在里面就会随同步走：

- 访问 S3 的密钥和 GitHub 令牌会出现在 S3 上的对象里，能读到这个对象的人就能拿到它们。
- 拉回时，另一台机器的凭证会盖掉本机的。
- 同步本身要先有凭证才能进行，新机器上的凭证没法靠拉回得到。

所以凭证和检查更新等应用设置一样，只属于这台机器。

## 为什么令牌和密钥存在系统里

`settings.json` 是明文：备份、复制目录或排查问题时把它发给别人，都会把令牌和密钥一起带出去。这三处都加密保存：macOS 钥匙串默认只有存进去的应用能直接读取，别的应用要读，得经用户在系统弹出的授权框里同意;Windows 凭据管理器按登录用户加密，只存在这台机器上，不随漫游配置文件走;Linux 的密钥环通常随登录解锁，锁着时由系统弹出解锁框。

其余几项不是秘密，Access Key ID 只是密钥的编号，所以和别的应用设置放在一起，打开文件就能看到和修改。

三项合成一个条目保存。在 macOS 上，应用的签名变了（ad-hoc 签名的应用每次构建都会变），系统会在应用第一次读取时询问是否允许，每个条目问一次;合成一个条目，用户只需确认一次。Windows 的单条凭据最多 2560 字节，Session Token 的长度 AWS 不保证，放不下时分成几条，最后才改写第一条，中途失败时旧内容仍在。

## 考虑过的选项

- **全部存进数据库**：一个文件就能带走全部配置，但凭证会随同步走，原因见上文。
- **全部存进 `settings.json`**：最简单，但令牌和密钥是明文。
- **Linux 上没有 Secret Service 时退回 `settings.json` 或只存在内存里**：前者是明文;后者退出就丢，用户以为存上了。所以没有时如实报读不到。

## 后果

- 换一台机器时，要在新机器的设置页重新填写，或者设置环境变量。拉回的库里没有凭证。
- 读不到时(macOS 上应用换了签名后第一次启动，用户拒绝了授权;Linux 上没在解锁框里解锁，或者没有 Secret Service——没有 D-Bus 会话、没装或没启动 GNOME Keyring / KWallet),启动时读不到令牌和密钥：令牌回到读环境变量；设置页填过同步设置的，同步缺密钥，不能进行。打开设置页时会再读一次，读到就恢复；仍读不到时，设置页不显示这两个分区的表单，免得把没读到当成没填，保存时盖掉存在系统里的内容。
- 卸载 Mechbox 时先删这个条目，删不掉就什么都不动，用户可以重试或跳过。
- server 模式(端到端验证用)在各平台上都不碰钥匙串、凭据管理器或密钥环，令牌和密钥只存在进程内存里。

# 用户操作流程：先入库，再安装

用户管理技能的全过程都围绕库展开：技能先从来源进库，再从库装到 Agent 那里。下面按阶段列出流程，每一步都对应 [CONTEXT.md](../../CONTEXT.md) 里的一个术语。

## 进库

1. **来源**：用户给出技能从哪里来。可以是搜索市场后选中的一条、一个 GitHub 链接、一个压缩包 URL，也可以是本机的一个目录。
2. **预览**：工具读出来源此刻的内容给用户看，库里什么都不写。预览钉在读取那一刻：之后来源再变，入库的仍是用户看到的版本。预览不用会过期，入库成功后作废。
3. **候选**：预览列出来源里可以入库的技能。看起来像技能但格式不对的文件夹会单独列出并说明原因，不算候选。
4. **入库**：用户勾选想要的候选，按预览时的内容放进库。新技能只能这样进库。
5. **更新**：已入库的技能以后可以检查更新，把来源的新版本直接带进库，不再经过预览。已经装出去的技能不会跟着变。

## 整理

6. **集合**：库里的技能按来源自动归成集合，用户不用操作。
7. **组**：用户按场景建组，比如"前端调试"，把来自不同来源的技能放在一起。

## 装出去

8. **作用域与已登记项目**：安装的目标是作用域，也就是某个 Agent 的全局，或者某个 Agent 加一个已登记项目。要装到某个项目里，先登记这个项目。
9. **安装计划**：用户选好技能或组、选好作用域后，先看安装计划，了解这次会做什么，比如目标位置是否已经有同名文件夹。
10. **安装与组安装**：确认后安装。安装单个技能是直接安装；安装一个组是组安装，之后加入这个组的技能也会自动装过去。用户能看到每个技能装在哪些作用域、每一处是直接安装还是随哪个组安装，以及每一处的状态：正常、被手动改过、落后于库里的版本，或者文件夹已经不在。
11. **重新安装**：库里有了新版本，或者装出去的文件夹不对了，由用户逐个作用域决定是否重新安装，让文件夹和库里的版本一致。这是唯一会覆盖已装文件夹的操作。
12. **卸载**：用户可以卸载单个技能，也可以卸载整个组。如果同一个技能在同一个作用域里既被直接安装、又随组安装，卸载其中一种，技能仍然保留；两种都撤销后，文件夹才会删除。

## 换机器

13. **同步计划**：推送或拉取之前，先看同步计划，了解这次会覆盖哪一份远端的库，或者从哪一份恢复。
14. **同步**：用户把整个库推送到 S3，在另一台机器上拉下来，再把已登记项目对应到这台机器上的路径。同步只在用户手动操作时发生。

## 为什么把入库和安装分成两步

- **一个技能可以装到多个 Agent、多个项目。** 库里只存一份，更新时从这一份出发，再决定装出去的哪些地方要跟上。
- **版本历史、组和同步都依附在库上**，而不是依附在某个 Agent 的目录上。
- **新技能只能经过预览入库。** 用户入库前能看清来源里有什么，入库的就是看到的内容。
- **更新只改库，不动已经装出去的技能。** 这样 Agent 正在用的技能，不会在用户不知情的情况下变掉。

## 考虑过的选项

- **一步到位，从来源直接装进 Agent 目录**（像生态里常见的技能命令行工具那样）。这种做法更简单，但有三个问题：同一个技能装在多处时，会变成多份互不相干的文件夹；既没有版本历史，也没法整组管理；换机器时也带不走整套配置。

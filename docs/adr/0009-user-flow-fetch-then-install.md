# 用户操作流程：先入库，再安装

用户管理技能的全过程都围绕库展开：技能先从来源进库，再从库装到 Agent 那里。完整流程如下：

1. **找技能**：用户搜索市场、贴一个 GitHub 链接，或选一个本地目录，得到一次预览，列出来源里的候选。看起来像技能但格式不对的文件夹，会单独列出并说明原因。用户勾选想要的候选，入库。
2. **整理**：库里的技能按来源自动归成集合。用户还可以按场景建组，把来自不同来源的技能放在一起。
3. **安装**：用户选一个技能或一个组，再选作用域，也就是某个 Agent 的全局，或者某个 Agent 加一个已登记项目。安装前先看安装计划，比如目标位置是否已经有同名文件夹，确认后再安装。装了组以后，之后加入这个组的技能也会自动装过去。
4. **查看**：对每个技能，用户能看到三件事：
   - 它装在哪些作用域；
   - 在每个作用域里，它是被直接安装的，还是随某个组安装的；
   - 每一处的状态：正常、被手动改过、落后于库里的版本，或者文件夹已经不在。
5. **更新**：用户检查更新，把来源的新版本带进库。已经装出去的技能不会跟着变，由用户逐处决定什么时候重新安装。
6. **卸载**：用户可以卸载单个技能，也可以卸载整个组。如果同一个技能在同一个作用域里既被直接安装、又随组安装，卸载其中一种，技能仍然保留。
7. **换机器**：用户把整个库推送到 S3，在另一台机器上拉下来，再把已登记项目对应到这台机器上的路径。

## 为什么把入库和安装分成两步

- **一个技能可以装到多个 Agent、多个项目。** 库里只存一份，更新时从这一份出发，再决定装出去的哪些地方要跟上。
- **版本历史、组和同步都依附在库上**，而不是依附在某个 Agent 的目录上。
- **新技能只能经过预览入库。** 用户入库前能看清来源里有什么，入库的就是看到的内容。
- **更新只改库，不动已经装出去的技能。** 这样 Agent 正在用的技能，不会在用户不知情的情况下变掉。

## 考虑过的选项

- **一步到位，从来源直接装进 Agent 目录**（像生态里常见的技能命令行工具那样）。这种做法更简单，但有三个问题：同一个技能装在多处时，会变成多份互不相干的文件夹；既没有版本历史，也没法整组管理；换机器时也带不走整套配置。

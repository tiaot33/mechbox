# 用户操作流程：先入库，再安装

用户管理技能的全过程都围绕库展开：技能先从来源进库，再从库装到 Agent 那里。下面按用户的操作顺序写出这个流程，加粗的词是 [CONTEXT.md](../../CONTEXT.md) 里的术语。

## 进库

1. 用户想找技能时，先给出一个**来源**：可以是市场搜索结果里的一条、一个 GitHub 链接、一个压缩包 URL，也可以是本机的一个目录。
2. 工具对这个来源做一次**入库预览**，把它此刻的内容读出来给用户看，库里什么都不写。入库预览钉在读取的那一刻：之后来源再怎么变，入库的仍是用户看到的内容。入库预览放着不用会过期。
3. 入库预览里列出可以入库的**候选**。看起来像技能但格式不对的文件夹会单独列出，并说明原因。
4. 用户勾选想要的候选，**入库**。新技能只能通过这种方式进库；入库后，这次入库预览就作废了。
5. 以后，**检查更新**会发现来源里的新版本。用户看过**更新计划**后**更新**，把新版本带进库，不用再做入库预览；同一次确认里勾选的作用域会**重新安装**成新版，没勾的保持原样。

## 整理

6. 库里的技能按**来源**自动归成**集合**，用户不用操作。
7. 用户还可以按场景建**组**，比如"前端调试"，把来自不同来源的技能放在一起。

## 装出去

8. 用户先决定装到哪里，也就是选一个**作用域**：某个 Agent 的全局，或者某个 Agent 加一个项目。项目要先登记进来，成为**已登记项目**。
9. 用户选好一个技能或一个组后，工具先给出**安装计划**，说明这次安装会做什么，比如目标位置是否已经有同名文件夹。
10. 用户确认后**安装**。装单个技能叫直接安装；装一个组叫**组安装**，之后加入这个组的技能也会自动装过去。
11. 之后，用户随时能看到每个技能装在哪些作用域、每一处是直接安装还是随哪个组安装，以及每一处的状态：正常、被手动改过、落后于库里的版本，或者文件夹已经不在了。
12. 如果库里有了新版本，或者某一处的文件夹出了问题，用户可以逐个作用域决定是否**重新安装**，让文件夹和库里的版本保持一致。只有重新安装会覆盖已经装好的文件夹。
13. 不再需要时，用户可以**卸载**单个技能，也可以卸载整个组。如果同一个技能在同一个作用域里既被直接安装，又随组安装，卸载其中一种后技能仍然保留；两种都撤销后，文件夹才会被删除。

## 换机器

14. 用户把整个库**推送**到 S3，成为这台机器的一份**备份**；推送也可以按用户设的间隔自动进行。
15. 在另一台机器上，用户选一份备份，先看**同步计划**，确认里面有什么、能不能拉回，再**拉回**，然后把已登记项目对应到新机器上的路径。拉回只在用户手动操作时才会发生。

## 为什么把入库和安装分成两步

- **一个技能可以装到多个 Agent、多个项目。** 库里只存一份，更新时从这一份出发，再决定装出去的哪些地方要跟上。
- **版本历史、组和同步都依附在库上**，而不是依附在某个 Agent 的目录上。
- **新技能只能经过入库预览才能入库。** 用户入库前能看清来源里有什么，入库的就是看到的内容。
- **装出去的地方只在用户确认时跟上。** 更新时用户在同一次确认里选择哪些作用域换成新版，没勾的保持原样。这样 Agent 正在用的技能，不会在用户不知情的情况下变掉。

## 考虑过的选项

- **一步到位，从来源直接装进 Agent 目录**（像生态里常见的技能命令行工具那样）。这种做法更简单，但有三个问题：同一个技能装在多处时，会变成多份互不相干的文件夹；既没有版本历史，也没法整组管理；换机器时也带不走整套配置。

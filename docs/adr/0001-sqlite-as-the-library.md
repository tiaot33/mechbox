# SQLite 就是 Library

Library 是本工具的唯一权威数据源，由一个 SQLite 数据库承载。它保存技能的**内容**（以 blob 形式）和全部**元数据**：集合、组、安装项及已登记项目。Agent 目录中的文件夹是它的副本，不是输入。

我们选择一个对外隐藏内部结构的存储，而不是磁盘上的技能文件夹，因为这样可以将权威数据源保持在唯一位置，为同时涉及多个技能的操作提供事务完整性，并让 S3 Sync 简化为“导出数据库，再推送”。Sync 不是实时同步，因此以整个 SQLite 数据库为单位的粗粒度方式没有额外代价：定期从 SQLite 导出的文件就是同步产物。

## 后果

- **Fetch**（入库）将预览过的技能文件以 blob 形式写入 SQLite。
- **Install**（安装）将技能从 SQLite 展开到目标 Agent 目录，形成一个 Installation；当不再有其他安装关系撑着它时，**Uninstall** 删除该文件夹。
- *（术语于 2026-09-27 更新：以上两条原先用“Install”表示写入 SQLite，用“Activation”表示展开到 Agent 目录。该约定已被 [ADR 0014](0014-install-means-agent-directory.md) 取代。）*
- 来自本地 Source 的技能通过工具编辑，而不是直接修改原处的文件。内容保存在数据库中，因此创作需要明确的导出／编辑／重新导入流程，或工具内的编辑器（待定义）。
- **Sync** 导出数据库并推送到 S3，也可拉取以恢复，从而在另一台机器上复现完整配置。

## Agent Skills 生态背景与集成边界

2026-09-14 补充，依据 [Agent Skills 背景](../agents/agent-skills-background.md) 中的 2026-09-12 调研。以下说明既有 SQLite 与“把技能文件夹放进 Agent 目录”决策在该生态中的含义。

Agent 消费的是含 `SKILL.md` 的目录，并按“元数据发现 → 正文加载 → 按需读取资源”使用技能。数据库只供 Library 管理内容；安装（Install）将文件还原到 Agent 的发现目录，Agent 因而无需读取 SQLite。这个边界既保留了 Library 的事务、历史和 Sync 能力，也适配客户端原有的文件发现机制。

- **保存整个 Skill 的文件集合。** `scripts/`、`references/`、`assets/` 等资源属于技能的一部分。渐进披露约束的是 Agent 何时读取内容，不意味着 Library 只保存 `SKILL.md`；相对路径与可执行位随版本保存，见 [ADR 0005](0005-content-addressed-skill-history.md)。客户端扩展字段及配套配置作为文件内容保留，其调用语义由客户端解释。
- **区分入库、安装和运行时加载。** 生态文档的“安装”指把文件夹放到发现目录，本项目的 Install 与之一致；进 Library 另称入库（Fetch）。这一约定见 [ADR 0014](0014-install-means-agent-directory.md)，它取代了本节最初“Install 指入 Library、Activation 指放入目录”的说法。规范所说的 Activation 是 Agent 加载正文，与本项目的任何操作都不同名。安装成功或存在安装项记录，只能说明本工具已提供文件，不能证明 Agent 已发现、选用或执行它。
- **Scope 表示 Agent 与管理层级。** 项目当前管理个人全局和 Registered project 两类层级；“全局”指当前用户跨项目，不代表企业、ADMIN 或 SYSTEM。目录名称来自 Agent 的发现约定，具体路径是 Scope 的落地位置。客户端从 CWD 向上扫描、嵌套加载、附加目录及插件启用等规则由客户端负责；登记一个项目不等于已复现这些规则。
- **区分安装冲突与客户端同名选择。** `ConflictPolicy` 处理写入同一目标目录时的冲突；客户端跨目录的同名优先级是另一件事。Claude Code 在企业、个人、项目之间覆盖，但嵌套与插件可并存；Codex 文档允许同名技能并存，未给出完整优先级。Library 的安装项记录不表示某个同名技能在会话中胜出，也不据此自动移除其他 Scope 的安装项。

这延续了以“把文件夹放进 Agent 目录”作为集成方式的选择：Library 管理技能内容与安装项状态，Agent 负责发现、选择和执行。完整路径与客户端规则集中在生态背景文档，避免把随客户端变化的行为固化为 Library 的通用规则。

### 当前实现差异

以下是文档与现有实现的对照，不代表已完成兼容性修复：

- **Codex 发现路径已改为现行 `.agents/skills`，旧目录不迁移。** Agent 布局由 Library 的 `agents` 表持有并以身份 Scope 解析（见 [ADR 0011](0011-scope-is-identity-not-path.md)）；Codex 种子为 `$HOME/.agents/skills` 与项目 `.agents/skills`。此前放到 `.codex/skills` 里的文件夹不会被搬迁或删除，需用户重新安装才落到现行目录(旧库本身不再迁移，见下文 2026-09-26)。旧路径是否仍被目标 Codex 版本发现尚未确认。
- **格式说明不等于完整规范校验。** [source_read.go](../../internal/library/source_read.go) 的候选解析检查 YAML 与安全名称，按 #59 要求 `description` 为必填字符串，未要求名称等于父目录名；本地目录的预览与远程来源用同一套候选解析，同样不等同于严格 frontmatter 验证。背景文档记录的必填项、长度与命名约束是开放规范要求，不能据此宣称 Library 已完整执行这些校验。

本次补充记录生态背景与已有设计边界；路径迁移和校验策略的实现需另行处理。

## 2026-09-26：未发布阶段不迁移旧版本库(#85)

- 产品尚未发布，没有需要保留的用户库。改 schema 时只改 `schema.sql` 并提升 `librarySchemaVersion`，不写迁移、不回填；全部 v1–v8 迁移代码已删除。
- `Open` 遇到应用标识或 schema 版本不符的库直接拒绝，不改文件；版本相符时再校验表与索引指纹和外键。
- 这取代了 ADR 0011 里"打开按路径记录的旧库时映射为身份、宁可丢行也不拒绝打开"的做法，以及 ADR 0005、0006、0007、0012 里关于迁移的描述。
- 发布后重新确认：届时需要迁移方案，并让桌面端能在迁移前先探知并备份。

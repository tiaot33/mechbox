# 同步按机器存多份备份：推送可以自动，拉回始终手动

S3 上不再只有一份库。每次推送都在这台机器自己的目录里新建一份备份：

```
<文件夹>/<设备目录>/library-<推送时间>.db
```

- **文件夹**由用户在设置里填，可以留空。对象名由库决定，不能设置。
- **设备目录**是主机名加一段随机后缀，第一次用到时生成，存在本机，不能改。它和同步设置一样只属于这台机器：推送时不带，拉回时保留。
- **推送从不覆盖备份。** 库和这台机器上一份备份内容相同时不新建。推完删掉这台机器超出保留份数的最旧备份（默认 10 份），别的机器的备份不动。
- **拉回**列出所有机器的备份，默认选最新推送的那份。用户看过那一份的同步计划再确认。
- **推送可以按间隔自动进行**（每小时、每天、每周）。间隔存在同步设置里，库只存取，定时由桌面端做。**拉回从不自动进行。**

## 为什么

- 只有一份库时，后推的机器覆盖先推的，看不出 S3 上那份来自哪台机器、哪一次，也退不回更早的状态。按机器分目录、每次新建，推送就不会互相覆盖，原来防止覆盖的「先看推送计划、执行时检查远端没变」也就不需要了。
- 自动推送只是多存一份备份，不改本机的库，也不改别的机器的备份，所以可以在后台进行。
- 拉回会整库替换：本机的改动会丢掉，设置也会换成那份备份里的。自动拉回会在用户不知情时换掉库，违背 [ADR 0010](0010-product-promises.md)「用户没有点头就不变」的精神，所以拉回始终要用户选定一份并确认。
- 「没变化就不新建」按快照里的内容判断，而不是按文件字节判断。只属于这台机器的设置行（例如上次推送的时间）变了，数据库文件的页面布局也会跟着变，按字节比就永远不相同。所以推送时给去掉本机设置后的快照逐表算摘要，存进对象的元数据。下一次推送只取这台机器最新那份备份的元数据比较，不用下载。

## 考虑过的选项

- **让用户填对象名**：之前的做法。多台机器要么共用一个对象互相覆盖，要么各填一个名字，但拉回时不知道 S3 上还有哪些名字。由库决定对象名，就能列出所有机器的备份。
- **设备目录直接用主机名**：两台主机名相同的机器（例如都叫 MacBook-Pro）会写进同一个目录，互相删对方的旧备份。加随机后缀后，各用各的目录。
- **自动同步也自动拉回，做成双向同步**：库以整个数据库为单位，两台机器各自改过以后没法合并，只能一边盖掉另一边。

## 后果

- 存储桶根下旧版本留下的 `library.db` 不迁移，新版本也不读它（发布前不迁移，见 [ADR 0003](0003-no-migrations-before-release.md)）。
- 备份的推送时间取对象名里的时间戳，也就是推送那台机器的时钟。几台机器的时钟有偏差时，列表里的先后会跟着偏。
- 同步要用到的 S3 权限多了列出（ListBucket）和删除（DeleteObject）。删旧备份失败时，推送报错，但这一份已经传上去了，下一次推送会再删。
- 自动推送失败的原因只记在桌面端的内存里，设置页显示出来；重启后由下一次自动推送重新得出。

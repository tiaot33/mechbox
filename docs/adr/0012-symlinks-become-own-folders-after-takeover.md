# 接管以后不保留符号链接：第一次写入时说明并换成独立的文件夹

用户的 Agent 目录里，技能文件夹常常是符号链接。`npx skills` 默认把真实文件夹放在 `~/.agents/skills/<name>`，再从其他 Agent 的目录链过去；技能作者也会把自己工作目录里的技能链进 Agent 目录。库自己安装时，每一处都写一份真实文件夹。

入库时磁盘上什么都不改，符号链接照样是符号链接。之后库第一次要写这一处时（更新、重新安装、回滚），在确认里说明这里原来是指向哪里的符号链接、之后会变成独立的一份，然后照常写成真实文件夹，不再写进链接指向的地方。

符号链接是 `npx skills` 这类命令行工具的管理手段：让几个 Agent 读同一份，由命令行工具统一更新。入库就是把技能交给 app 管，之后再用命令行工具更新，app 只能报为被手动改过（见 [Agent 目录里已有技能的产品逻辑](../product/existing-skills.md)）。app 接手以后，用自己的手段让各处保持一致：更新时连带重新安装装过的各处，在一处改了，用这里的修改更新到其他地方。所以接管以后再保留链接，用户得不到额外的东西；刚更新完，各处都是新版本，Agent 的表现和保留链接时一样。用户失去的只是在一处改、别处立刻跟着变，换来的是多一次确认，而这正是 [ADR 0010](0010-product-promises.md) 要的：用户没有点头，Agent 用的技能就不变。

只有一种链接例外：**指向 Agent 目录以外的符号链接，默认不接。** 典型的是技能作者把 `~/.claude/skills/foo` 链到自己的工作目录 `~/code/my-skills/foo`，在那里改了，Agent 马上就能用上。接管后链接一换成独立的一份，作者在工作目录里怎么改，Agent 都看不到了。所以这类技能照样列出、写明指向哪里，但和在项目仓库里的一样默认不入库；用户自己勾上时写清这一点。作者真想交给 app 管，更合适的做法是把工作目录作为本地目录来源入库，改完重新读取。

## 考虑过的选项

- **一直保留链接，写进链接指向的真实文件夹。** 用户的布局一直不变，但每一条写磁盘的路径都要先解析链接、按真实文件夹去重：安装覆盖、重新安装、更新、回滚、卸载、移除技能、自定义 Agent 改目录。还要处理指向 Agent 目录以外的、悬空的、指向别的磁盘的链接，界面上把同一个文件夹的几处并成一行。这些以后每个新功能都要再考虑一遍，换来的只是接管后用户已经不需要的东西。
- **入库时就把链接换成独立的文件夹。** 实现最简单，但违背了入库时磁盘上什么都不改；这是用户敢一次全选的前提。
- **保持原来的行为，悄悄换掉。** 更新以后链接没了，用户在原来的真实文件夹里改，另一个 Agent 不再跟着变，却不知道为什么。
- **库自己安装时也用符号链接。** 改一处就处处都变，没有确认、不能回滚；提交在项目仓库里的链接指向这台机器上的路径，到别人的机器上是断的；app 的数据被删，所有 Agent 一起丢技能。

## 后果

- **链接只在库要写那一处时才换。** 入库、巡检、列出都不动它；巡检和入库读的是链接指向的内容。
- **换之前在确认里说出来。** 更新计划、重新安装和回滚的确认里，是符号链接的那一处写明它指向哪里、之后会变成独立的一份。没有链接的用户看不到这句话。
- **库要删一个被链接指向的真实文件夹时，先给指向它的各处换上独立的一份。** 比如从 Codex 卸载 tdd，Claude Code 里还装着指向它的链接：先让 Claude Code 那一处成为独立的一份，再删，并在确认里说出来。否则用户只动了一个 Agent，另一个 Agent 的技能却跟着没了。
- **还没换之前，指向同一个真实文件夹的几处按一个文件夹说。** 比如用这里的修改更新时，不把另一处当成也改过的地方。
- **指向 Agent 目录以外的链接默认不入库。** 在第一次打开和登记项目后的确认里默认不勾，勾上才写清之后在 app 里更新会把它换成独立的一份；作用域里那一行「还有几个没入库」不算它们，理由和在项目仓库里的一样，用户是有意不交给 app 的。Agent 目录指的是各 Agent 在全局和已登记项目里读取技能的目录。

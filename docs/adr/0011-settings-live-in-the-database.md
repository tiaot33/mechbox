# 设置都存在数据库里，不读环境变量

从访达或 Dock 启动的桌面端读不到 shell 里的环境变量（[ADR 0008](0008-desktop-is-wails-v3-in-process.md) 的后果），所以设置页要能填 GitHub 个人访问令牌、同步用的 S3 设置，以及检查更新、通用、Agent 显示这些应用设置。

这些设置都存在数据库的 `config` 表里，一项一行，库只认这里：

- 不读环境变量（`GITHUB_TOKEN`、`GH_TOKEN`、`SKILLS_S3_*`、`AWS_*`）。
- 不另存在系统钥匙串或数据库旁边的设置文件里。

设置分两种：

- **只属于这台机器**：S3 同步设置、各 Agent 的全局目录所在的 WSL 发行版。推送出去的库里不带，拉回时保留本机的。
- **其余设置随推送、拉回走**：GitHub 令牌和应用设置。拉回后换成拉回的那份库里的，那份库里没有的就变成没填。

## 为什么只认数据库

环境变量和设置页同时有效时，用户看到设置页里填的是一个值，实际生效的可能是 shell 里的另一个。这类问题只能靠「哪个优先」的规则解释，排查起来很难。只认一个来源，设置页显示的就是实际生效的值。

设置全在数据库里，也带来两个好处：

- 用户换机器、重装后，拉回整个库，令牌和应用设置跟着回来。
- 卸载时删掉数据库，所有设置一起删掉，不会在系统钥匙串里留下条目。

## 为什么 S3 设置和 WSL 发行版只属于这台机器

- 新机器得先填好 S3 才能拉回。拉回时如果换成那份库里的 S3 设置，可能盖掉这台机器刚用来连上 S3 的设置。推送那台机器用的是另一把 Access Key，或者那份库里根本没有 S3 设置时，这台机器之后就推不上去了。
- WSL 发行版的名字只在装着它的那台 Windows 机器上有意义。
- 推送出去的库里不带 S3 设置，S3 上的对象里就没有 S3 的密钥。

## 考虑过的选项

- **环境变量优先，没有再读数据库**：会出现上面说的两个来源不一致的问题。很多人的 shell 里本来就设了 `AWS_*`，设置页填的会莫名失效。
- **密钥存在系统钥匙串里**：之前的做法。macOS 上应用换了签名会再弹授权框；Linux 上没有 Secret Service 时读不到；卸载时还要单独删条目。数据库本来就存着令牌，能读到数据库的人也能读到技能库的全部内容。所以这一步加密挡不住多少，代价却不小。
- **应用设置存在 `settings.json` 里**：数据就有了两个来源。卸载、换机器时要分别处理两处。

## 后果

- 密钥以明文存在数据库里。打开数据库时把文件改成只有当前用户能读写；数据库开着 `secure_delete`，清空或换掉的值在文件里清零。
- 之前的版本存在系统钥匙串、凭据管理器或 Secret Service 里的条目（服务名 `com.tiaot33.mechbox`）不迁移，卸载时也不删除（发布前不迁移，见 [ADR 0003](0003-no-migrations-before-release.md)）。用过的话要手动删除。
- 换一台机器时，先在设置页填好同步设置再拉回，令牌和应用设置随库回来。
- 本地调试时用 `MECHBOX_LIBRARY` 让桌面端打开另一个数据库。这个变量只决定打开哪个数据库，不覆盖任何一项设置。换一个数据库就是换一整套设置，不会和真实技能库的设置混在一起。
- 端到端验证需要的令牌由测试脚本在设置页里填写，应用本身不读环境变量。

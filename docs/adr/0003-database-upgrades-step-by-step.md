# 数据库从 schema 版本 27 起逐版升级，升级 SQL 由命令生成

Mechbox 已经在发版：main 上每合进几个改动就自动发一版，app 里能直接更新，覆盖安装后数据库原样留着。只要两个版本之间数据库结构变了，新版就得能打开旧版建的数据库，里面的技能、来源、备注和设置都要留着。

所以：

- **从 `user_version` 27 起支持升级。** v0.0.2 到 v0.0.6 建的数据库都是 27。只有 v0.0.1 建的（24）不升级，`Open` 照旧拒绝打开、不改动文件。
- **版本号只有 `PRAGMA user_version`。** 每改一次结构，`store/migrations/` 下加一个按 goose 命名的文件 `NNNNN_<做了什么>.sql`（需要用 Go 转换数据时是 `NNNNN_<做了什么>.go`），编号就是跑完它之后的 `user_version`，从 28 起连续不断。新建的数据库直接执行 `schema.sql`，不跑升级。
- **打开旧数据库时逐版升级。** 先在数据库旁边留一份备份 `library-v<旧版本>.db`，再一版一版升。全部升级在一个事务里执行：事务外关掉外键，跑完做 `foreign_key_check` 和表结构校验再提交，任何一步失败都整个回滚，数据库保持原样。另一个进程已经升级过时，不再拿升级后的数据库覆盖备份。同步拉回的旧备份在临时文件上走同一套升级。
- **改表一律按 `schema.sql` 原文整表重建，不用 `ALTER TABLE ADD COLUMN`。** 新表的建表语句从 `schema.sql` 原样复制（连注释），拷数据、抄 `AUTOINCREMENT` 的计数器、换名、重建索引。这样升级后的数据库和新建的数据库建表语句一致，`Open` 的表结构校验照旧按原文比对（只把改名后带引号的表名当成不带引号）。
- **升级 SQL 由命令生成。** 改完 `schema.sql` 后运行 `go run ./internal/library/internal/store/migrationgen <做了什么>`：它在内存里把 27 版的结构（`store/testdata/00027_schema.sql`，取自 v0.0.6）跑完已有的升级，和 `schema.sql` 逐表比较，写出下一版的升级文件，并确认跑完它结构就等于 `schema.sql`。新加的列是 `NOT NULL` 或主键、又没有默认值时它停下来，要手写；删掉的表和列它会提示，可能是改名。
- **CI 守住两件事。** 改了 `schema.sql` 却没生成升级时测试失败；最近一个发布 tag 里已有的升级文件和起点结构不能改。自动发版前照常跑 `go test`。

## 考虑过的选项

- **Atlas 生成、goose 执行。** Atlas 在我们的表结构上每次都会生成多余的删建索引语句（`UNIQUE` 约束被当成索引，ariga/atlas#1597），重建表会丢掉 `AUTOINCREMENT` 的计数器、写出的建表语句和 `schema.sql` 原文对不上；它在 goose 文件里写的关外键语句在事务里不起作用。生成的每个文件都得手改。
- **只用 goose 执行手写的 SQL。** 默认会往用户数据库里加一张版本表（进到表结构校验和同步摘要），在事务里关不掉外键，数据库比 app 新时不报错。这些都要另写代码绕开，省下的和自己写一个循环差不多。
- **`ALTER TABLE ADD COLUMN`。** SQLite 会把新列插进原来建表语句的中间，和 `schema.sql` 对不上，表结构校验就只能放松。

调研见 [SQLite 数据库升级：Atlas 与 goose](../research/sqlite-migrations-atlas-goose.md)。

## 升级文件多了：挪起点

升级文件默认全部保留：每个只有几 KB，打开数据库时只跑比它新的几步，CI 从起点一路升到最新也很快。Go 写的升级步骤只用传进来的事务和 SQL，不引用别的代码，留多久都不用维护。

决定不再支持某个版本之前建的数据库时（时机跟产品节奏走，比如发 v0.1.0、1.0），手动挪一次起点。以挪到 `user_version` 40、对应发布版本 v0.3.0 为例：

1. 用 `git show v0.3.0:internal/library/internal/store/schema.sql` 写出新的起点结构 `store/testdata/00040_schema.sql`，删掉旧的 `00027_schema.sql`；`schema.go` 里的 `oldestVersion` 改成 40，`baselineFile` 指向新文件。
2. 把 `store/testdata/00027_data.sql` 换成 40 版的样例数据 `00040_data.sql`：用旧样例建 27 版数据库，跑完到 40 的升级，再导出每张表的数据。样例里每张表都要有行，测试会检查。
3. 删掉 `store/migrations/` 里编号不超过 40 的升级文件。
4. 改 `.github/scripts/check-migrations.sh`：它把删除已发布的升级文件当成错误，挪起点的这个 PR 里要允许删除编号不超过新起点的文件和旧的起点结构。
5. 改本文和 `Open`、`CannotPullOlderApp`、`FailedPrecondition` 的 doc comment 里"哪些版本不升级"的说法，重新生成前端绑定。

比 40 更早建的数据库从此和现在 v0.0.1 建的一样：拒绝打开、文件不动。用户可以先装一个中间版本（v0.3.0 起、挪起点之前的任一版）打开一次升到 40，再装新版。不采用 Chromium、Room 那样对太旧的版本直接清空重建：技能库里的数据只有用户自己有。

也考虑过让新的大版本发布后由 CI 自动开挪起点的 PR，或在打包时按 tag 自动挪：前者为偶尔做一次的事多维护一套流程，后者打出的安装包和 main 上测过的代码不一样，都不采用。

## 后果

- 改哪张表就整表复制一次，比如以后改存文件内容的 `blobs` 表，要把所有文件内容复制一遍。
- 备份文件不自动删除，用户退回旧版 app 时可以拿它换回来；卸载时和数据库一起删掉（里面有明文的令牌和密钥）。
- 表内列上的注释也算结构：改一个字也要生成一步升级（整表重建）。
- v0.0.1 建的数据库只能移走重来；同步时这样的备份报"来自较旧版本的应用"。

# Scope is an identity, not a path

A **Scope** is one of exactly two kinds — an Agent's global level, or an Agent together with one Registered project — and the Library, not the caller, holds each Agent's current layout (the directory names it scans under `$HOME` and under a project root). An Installation records only the Scope identity; the target directory is derived from the layout at the moment of listing or installing. Nothing on the facade accepts a directory to install into, and there is no method that lists "all scopes with their paths".

We chose this over the earlier `Scope{Agent, Path}` because the directory name is the Agent vendor's decision, not the user's: when Codex moved from `.codex/skills` to `.agents/skills`, a path-shaped Scope forced the same suffix rule to be repeated in the target list, in per-project expansion, in Sync remapping and in every test, and an Installation keyed by absolute path had to be *guessed* into a new `$HOME` after Sync. Keying on identity means a layout change is one row in `agents`, and the same Installation resolves correctly on any machine. (Terms updated per [ADR 0014](0014-install-means-agent-directory.md): Activation → Install, Projection → Installation.)

## Considered options

- **`Scope{Agent, Path}` (rejected).** Lets a caller install anywhere; makes the Library a copy tool rather than the owner of where Agents look. Bakes stale directory names into records.
- **One struct with an optional project field (rejected, later superseded).** Hides the two kinds behind a nullable; the two levels are different things, so they were first two Go types (`GlobalScope`, `ProjectScope`) behind a sealed `Scope` interface. **2026-09-25 (ADR 0013):** the facade must round-trip through JSON for the Wails desktop client, and an interface parameter can be neither unmarshalled nor bound. `Scope` is now one struct `{Kind, Agent, ProjectID}` with an explicit `Kind` (`global` | `project`), built by the constructors `GlobalScope(agent)` / `ProjectScope(agent, projectID)`. The explicit `Kind` answers the original objection: the two kinds are named, not inferred from an empty field, and every method that takes a `Scope` rejects an invalid combination (global with a project, project without one, unknown kind) as `invalid_argument` with `Details.Field`.
- **User-editable Agent layouts (rejected).** Would let a Scope point where the Agent never scans. Layouts are seeded and repaired by the product; there is no facade to change them.

## Consequences

- `Install` / `Uninstall` / `InstallGroup` / `UninstallGroup` / `Resolve` take a `Scope` identity. Unknown Agent code or unregistered project → `NotFound`. Callers compose targets from `ListAgents` × (global | `ListRegisteredProjects`); `ListScopes` is gone.
- `ListInstallations` returns `{SkillID, Scope, Directory, Direct, Groups, CreatedAt}` (renamed by #91 / #85 / #110). `Directory` is derived read-only; it is not accepted back as input.
- Installation health is produced by the Library comparing each Installation against disk (`InspectInstallations`); callers render the status and do not inspect disk themselves.
- Storage keys an Installation (and a Group install) by `(skill or group, agent, project_id NULL|id)`; no path column. Sync remaps only Registered project paths — Installations need no rewriting, since directories are re-derived from the local `$HOME` and the mapped roots.
- **The Library never creates a Scope root** — the user's home directory for global, the registered path for a project — only the Agent's layout directories below it. A missing root means the project is not on this machine (synced from another machine, moved, or on an unmounted drive); `MkdirAll` would conjure the whole path on the system disk. `Install` / `InstallGroup` fail with `failed_precondition` (`Details.Path` = root, plus `ProjectID` for a project) and record nothing; adding a Group member skips that Scope. (2026-09-26, #85)
- **Layout changes do not migrate disk.** After a vendor changes its layout, only the current directory counts; folders the tool installed into a former directory are stale and are neither moved nor deleted. Users install again to place skills into the current directory.
- **Opening an older library is refused, not mapped** (2026-09-26, #85; see ADR 0001). This ADR originally mapped path-keyed installation records of a pre-identity library to identities and preferred dropping unrecognised rows over refusing to open. While the product is unreleased there are no user libraries to keep, so all migrations were removed: `Open` rejects any library whose application id or schema version differs, without touching the file.
- `Scope` serialises as `{"kind", "agent", "project_id"?}` in both directions; the `Scope` a caller reads from `ListInstallations` is the one it passes back to `Uninstall`. Identity-not-path is unchanged: still no directory on the wire.

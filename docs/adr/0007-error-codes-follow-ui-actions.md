# 错误码按界面要做的动作划分

库返回的每个错误都带一个稳定的错误码和结构化的细节，界面根据它们决定怎么反应，不去解析错误消息。错误消息是写给开发者看的英文。

错误码按界面要采取的动作来划分，而不是按故障原因分类。界面的动作有这几种：让用户改输入、让用户先改状态、提供重试、静默收起、当作 bug 报告。两种故障只要界面的处理方式相同，就共用一个码；只有界面确实多了一种处理方式，才新增一个码。

举个例子："来源连不上"可以重试；"来源能连上但内容不能用"重试也没用，应该换一个来源。所以这两种情况分成两个码。而各种说不清原因的 I/O 故障，界面都只能当 bug 报告，所以统一归为 `internal`。

细节是有类型的结构，比如出问题的字段、技能或路径，而不是字符串键值对。这样前端的 TypeScript 类型可以直接生成。

## 后果

- 凡是由调用方引起的错误，库都必须显式返回带码和细节的错误。只有漏网的数据库约束错误，才由统一的兜底逻辑归类，而且不带细节。
- 每个码的适用场景和界面该怎么处理，写在 `api.go` 的错误码注释里。

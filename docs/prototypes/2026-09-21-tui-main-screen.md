# 原型:技能管理器主界面该长什么样

**日期:** 2026-09-21
**分支:** `worktree-prototype-tui`(一次性,不进 main)
**跑法:** `GOWORK=off go run ./cmd/prototype-tui`,`←`/`→` 切换变体;
`-dump` 不进交互界面,把三个变体依次打印到 stdout。

## 问题

三个结构上彼此不同的主界面变体,跑在同一份真实数据上,用来决定:**这个工具的主界面,
主要可供性是「浏览库里有什么」,还是「管理哪儿开着什么」,还是「处理出问题的东西」?**

这是本仓库第一个真实调用 `internal/library` 门面的程序 —— 此前只有 `cmd/demo` 打印一行
Agent 列表。技术选型沿用 ADR 0002 的 Bubble Tea。

## 数据不是假的

原型在临时目录里建了一个隔离环境:8 个技能(带 frontmatter 描述)、2 个分组、
2 个已登记项目、2 个 Agent → 6 个 Scope,以及真的投影到磁盘的激活记录。
随后故意扰动磁盘,凑齐 `InspectActivations` 的几种状态:删文件夹(`missing`)、
改内容(`modified`)、删整个 Scope 目录(`directory_missing`)。

**注意**:`library.Open` 在打开时捕获 `os.UserHomeDir()`,全局 Scope 的投影据此落盘。
原型必须在 `Open` 之前把 `HOME` 改到临时目录,否则会写进用户真实的 agent 目录。

## 三个变体

| | 主要可供性 | 信息层级 | 代价 |
|---|---|---|---|
| **A 双栏浏览** | 浏览目录 | 技能为主,投影状态是详情里的附属区块 | 「哪儿开着什么」要逐个技能点开才看得到 |
| **B 激活矩阵** | 管理投影 | Scope 为主,技能只剩一个名字 | 描述、来源、版本全部无处安放;Scope 一多就横向溢出 |
| **C 待办流** | 处理异常 | 按严重度排序,正常的折叠成一行计数 | 没有目录感,想找某个具体技能只能靠搜索 |

## 门面发现(这才是跑这一轮的主要收获)

这是门面第一次被真实调用方使用,暴露出的缺口:

1. **`Open` 无法注入 home,只能改进程级 `HOME`。** 任何想在隔离环境里跑的调用方
   (测试、原型、沙箱)都得动环境变量。这是进程级副作用,并发场景下不成立。

2. **`Scope` 没有相等比较,也没有显示名。** 密封接口,调用方要自己写类型 switch 做比较
   (本原型的 `sameScope`),还要自己拼「Claude Code · 全局」这类标签。每个调用方都会
   重写一遍同样的代码。Roadmap 把 wire 形状推给了 RPC 层,但**进程内调用方同样需要**。

3. **没有「可用 Scope 列表」方法。** `api.go` 的注释明说「调用方用 ListAgents ×
   (全局 | ListRegisteredProjects)自行组合」。矩阵视图第一件事就是要这个列表,
   组装它花了约 20 行。这是每个调用方都要做的同一件事。

4. **投影列表不能按 skill 或 scope 过滤**(Roadmap 里 C8 被推后了)。填矩阵必须先建一个
   `skillID × scope → 状态` 的索引。同样是每个调用方都要重写的东西。

5. **本地安装产生不了多技能 Collection。** `Install` 是一个目录一个技能,所以 8 个技能
   = 8 个单元素 Collection。Collection 这个概念在纯本地数据上完全没有意义,只有远程来源
   才能触发它。

## 设计发现

**待办流按 Activation 记录逐条列,会重复报同一个成因。** 一个 Scope 目录没了,
底下有几个技能就报几条。待办流必须按**成因**聚合(「skills-app 的目录没了,影响 2 个技能」),
而不是按投影记录。这条对变体 C 是结构性的,当前实现故意保留了这个缺陷以便看清它。
